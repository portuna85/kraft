# 인스턴스별 상태 목록 (A-OPS-06)

이 서버는 단일 인스턴스를 전제로 짜여 있다. 아래는 그 전제에 기대는 상태를 한곳에 모은
표다 — 재시작(현재의 배포 방식) 때 무엇이 초기화되는지, 인스턴스를 두 개 이상 띄우면(무중단
배포 A-OPS-03의 두 포트 방식, 또는 장래의 수평 확장) 무엇이 깨지는지, 공유 저장소로 옮길 때
무엇으로 대체할 수 있는지를 여기서 먼저 확인한다. 코드를 지금 바꿀 필요는 없다 — 판단 자료다.

| 상태 | 위치 | 재시작 시 영향 | 다중 인스턴스 시 영향 | 공유 저장소로 옮길 때 |
| --- | --- | --- | --- | --- |
| 요청 속도 제한 카운터 | `FixedWindowRateLimiter`(로그인·가입·비밀번호 재설정·추천 3종) | 카운터가 0으로 리셋 — 재시작 직후 잠깐 제한이 느슨해진다 | 인스턴스마다 따로 세어, 실제 허용치가 인스턴스 수만큼 커진다(우회 가능) | Redis `INCR`+TTL, 또는 DB 테이블 + `FixedWindowRateLimiter`와 같은 API |
| 홈 화면 인기글 캐시 | `CacheConfig`(Caffeine, `spring.cache.caffeine.spec`) | 캐시 비고 처음 요청이 다시 계산 | 인스턴스마다 캐시가 따로 놀아 갱신 시점이 어긋난다(같은 페이지가 인스턴스별로 다르게 보일 수 있음) | Redis(`spring-boot-starter-data-redis` + `@Cacheable`), TTL은 그대로 유지 |
| 업로드 정리 진행 지점 | `OrphanFileReconciler.skipOffset` | 0으로 리셋 — 다음 주기가 처음부터 다시 훑는다(정상 동작, 최후 수단 성격) | 두 인스턴스가 동시에 같은 파일을 훑어 삭제를 두 번 시도할 수 있다(멱등이라 안전하지만 로그가 중복됨) | DB에 "마지막으로 본 파일 경로/시각"을 저장, 또는 `ShedLock`류로 실행 자체를 한 인스턴스로 제한 |
| 추천 이력 스냅샷 캐시 | `RecommendationHistoryProvider.cached`(`volatile`) | 비어서 다음 요청이 DB에서 다시 읽음(정상 동작 — 기동 시 강제로 채우지 않음) | 인스턴스마다 다른 시점의 스냅샷을 볼 수 있다(짧은 창, `version` 비교로 스스로 갱신하므로 영구적이지 않음) | 이미 DB가 진실 소스라 캐시를 아예 없애도 정확성에는 문제없다 — 순수 성능 최적화 |
| 동행복권 조회 결과 캐시 | `DhLotteryClient.cache`(`ConcurrentHashMap`) | 비어서 다음 조회가 외부 API를 다시 호출 | 인스턴스마다 따로 캐시해 외부 호출 횟수가 인스턴스 수만큼 늘어난다(A-OPS-08의 서킷과도 상호작용) | Redis, 또는 이미 있는 `recommendation_winning_draws` 테이블을 캐시로도 겸용 |
| 세션 | Spring Session JDBC(`spring.session.store-type: jdbc`) | **영향 없음** — 이미 DB에 있다 | **영향 없음** — 어느 인스턴스가 받아도 같은 세션을 본다 | 해당 없음(이미 공유 저장소) |
| 아웃박스 메일 발송 | `OutboxMailStore`/`OutboxMailWorker` | **영향 없음** — DB 행 + `SKIP LOCKED`로 인스턴스 수와 무관하게 안전 | **영향 없음**(설계상 다중 소비자를 전제) | 해당 없음 |
| 세션 폐기 대기열 | `SessionRevocationStore`/`SessionRevocationWorker` | **영향 없음** — 위와 동일하게 DB + `SKIP LOCKED` | **영향 없음** | 해당 없음 |

마지막 세 줄(세션·아웃박스·세션 폐기)은 이미 DB를 진실 소스로 쓰고 있어 다중 인스턴스에
안전하다 — 무중단 배포나 수평 확장을 검토할 때 새로 손볼 필요가 없는 부분이다. 위 다섯
줄(속도 제한기부터 동행복권 캐시까지)이 실제로 검토 대상이다.
