## 1. 결론

현재 프로젝트는 Spring Boot와 Next.js의 역할 분리, 마이그레이션 기반 DB 관리, 추천 이력 결손 시 fail-closed 처리, 폭넓은 단위·통합·E2E 테스트, CSP와 컨테이너 보안, 번들 예산 및 관측 지표까지 갖췄다. 이번 실행에서 프론트엔드 린트·타입 검사·단위 테스트·프로덕션 빌드, Chromium/Firefox/WebKit E2E, Linux 픽셀 기준선, 백엔드 테스트·정적 분석과 실제 OpenAPI 계약 일치를 다시 검증했다.

감사 시작 시 출시 품질 관점에서 우선 해결 대상으로 식별한 항목은 다음과 같았으며, 현재는 모두 위 감사 표와 §13의 상태로 처리됐다.

1. **추천의 “역대 1등 당첨 조합 제외”를 단순한 UI 기본값이 아니라 전체 스택의 상시 불변식으로 보장한다.**
   감사 시작 시 백엔드는 모든 전략에서 과거 조합을 제외하고 이력 누락 시 503으로 거절했지만, 새 회차 커밋 직후 비동기 스냅샷 갱신 사이의 경쟁 구간, 다중 인스턴스의 프로세스 로컬 캐시 불일치, DB 독립 제약 부재, 추천 이력 상태의 readiness 누락 문제가 남아 있었다.
2. **개인정보처리방침을 실제 OAuth·커뮤니티·광고·세션 데이터 처리와 일치시킨다.**
   감사 시작 시 문구는 익명 기기 토큰과 저장 번호만 보관하며 이름 등은 수집하지 않는다고 설명했지만, 실제 시스템의 OAuth 제공자 식별자, 닉네임, 프로필 이미지, 게시글·댓글·신고·반응·차단·세션 처리를 반영하지 못했다.
3. **모바일에서 핵심 정보가 잘리는 화면을 우선 수정한다.**
   감사 시작 시 모바일 홈의 당첨금 표는 세후 금액 열과 금액이 시각적으로 잘렸고, 커뮤니티 목록 메타데이터는 한 행에 과도하게 압축됐다. 당시 “페이지 전체 가로 오버플로 없음” 검사는 이와 같은 내부 잘림을 잡아내지 못했다.
4. **실패 상태를 빈 상태로 위장하지 않는다.**
   감사 시작 시 홈 커뮤니티 요약과 계정 보관함은 요청 실패를 빈 배열 또는 `null`로 바꿔 “아직 글이 없습니다” 또는 아무것도 표시하지 않는 상태가 됐다. 저장·추천 이력 삭제 실패도 사용자에게 충분히 전달되지 않았다.
5. **접근성 프리미티브와 반응형 CSS의 구조적 부채를 정리한다.**
   감사 시작 시 라디오형 세그먼트 컨트롤의 키보드 포커스 이동, 포커스 트랩의 빈 대화상자 처리, 배경 스크롤·비활성화가 불완전했다. 전역 CSS는 700줄 이상이었고 중복 브레이크포인트와 예외 규칙이 많았다.

실제 실행 순서는 **P0 정책·정합성 → P1 모바일 핵심 흐름·오류 상태·접근성 → P1 API/DB/운영 보장 → P2 CSS·컴포넌트·프록시 구조 개선 → 전체 재검증**이었다.

## 2. 분석 범위와 방법

### 2.1 저장소 인벤토리

Git 추적 파일 830개를 경로, 확장자, 크기, 역할 기준으로 분류했다.

| 영역 | 파일 수 | 주요 내용 |
|---|---:|---|
| `web/` | 427 | Next.js App Router, React 컴포넌트, CSS, API 프록시, Vitest, Playwright, 120개 시각 기준 이미지 |
| `src/` | 334 | Spring Boot 소스·테스트, Thymeleaf 관리자 화면, 설정, 29개 SQL 마이그레이션 |
| `scripts/` | 31 | 배포, 검증, 드리프트 검사, 부하 테스트, 데이터 마이그레이션 |
| 저장소 루트 | 17 | Gradle, Docker Compose, 환경 예시, README, 패키지 설정 |
| `.github/` | 6 | CI, CodeQL 및 자동화 설정 |
| `infra/` | 6 | Prometheus, Alertmanager, Grafana 관련 설정 |
| 기타 | 9 | Caddy, Gradle wrapper 등 |

주요 확장자는 Java 295개, TSX 132개, PNG 120개, TypeScript 102개, CSS 45개, SQL 29개, 셸 스크립트 26개, YAML 17개다. 프론트엔드 텍스트 소스는 생성 API 타입과 lock 파일을 포함해 약 2.86만 줄이다.

분석 방식은 다음과 같다.

- 텍스트 소스: 경로·의존 관계·도메인별 검색, 주요 진입점과 오류 경로, 테스트 및 설정 상호 대조
- SQL: 테이블·제약·인덱스·외래 키·추천 이력 저장 구조 점검
- 프론트엔드: 모든 App Router 페이지, 공용 컴포넌트, UI 프리미티브, 전역·반응형 CSS, API 클라이언트와 프록시 점검
- 시각 자료: 120개 PNG의 파일 건전성 확인과 홈·추천·커뮤니티의 모바일·데스크톱 대표 기준 이미지 직접 비교
- 테스트·운영: Vitest, Playwright 설정, CI, Docker Compose healthcheck, Prometheus 경보, API 타입 드리프트 및 번들 예산 점검
- 바이너리·생성물: 이미지 메타데이터와 대표 렌더링을 확인했으며, 생성 타입과 lock 파일은 직접 설계 대상이 아니라 생성 경로와 소비 방식 중심으로 확인했다.

“전체 파일 분석”은 모든 파일을 동일한 깊이로 한 줄씩 설명한다는 의미가 아니라, 전체 인벤토리를 누락 없이 분류한 뒤 실행 경로와 위험도에 따라 의미 분석 깊이를 높이는 방식으로 수행했다.

## 4. P0 — 역대 1등 당첨 조합 제외를 전체 스택 불변식으로 보장

### 4.1 제품 정책

추천 결과의 기본 정책은 다음 문장으로 고정한다.

> 추천 번호는 생성 시점에 DB에 확정되어 있는 역대 모든 1등 당첨 번호 6개 조합과 동일할 수 없다. 이 정책은 모든 추천 전략, 로그인 여부, 저장 여부, 클라이언트 종류에 동일하게 적용되며 사용자가 해제할 수 없다. 이력을 완전하게 확인할 수 없으면 추천을 생성하지 않는다.

“기본으로 선택된 체크박스”는 사용자가 끌 수 있으므로 위 요구를 만족하지 않는다. UI에는 비활성화 가능한 옵션 대신 **상시 적용되는 정책 안내**로 표시한다. 만약 향후 상품 요구로 해제 기능을 검토한다면, 이는 기본값 변경이 아니라 안전 정책 변경으로 별도 승인·법무 검토·API 버전 변경이 필요하다.

### 4.2 현재 구현

현재 구현은 이미 상당 부분 요구를 충족한다.

- `LottoRecommendationService`는 시작 시 `WinningNumberRepository.findAllBalls()`로 모든 회차의 6개 번호를 읽어 45비트 조합 마스크 집합을 만든다.
- 스냅샷은 데이터가 존재하고 1회부터 최신 회차까지 중간 누락이 없을 때만 `ready`다.
- 추천 요청 시 스냅샷이 준비되지 않았으면 `503 RECOMMENDATION_HISTORY_NOT_READY`로 거절한다.
- `random`, `balanced`, `reduce_shared_winner_risk` 전략은 모두 동일한 역사 조합 마스크를 거쳐 생성된다.
- 실제 후보 반환 직전에도 `historicalMasks.contains(bitmaskOf(result))`를 검사한다.
- 응답과 저장 추천 세트에 `historyThroughRound`를 기록한다.
- 신규 또는 변경 당첨 번호가 커밋되면 `AFTER_COMMIT` 이벤트로 스냅샷을 다시 읽는다.
- `kraft_lotto_history_ready`, `data_present`, `round_count`, `first_missing_round` 지표와 관련 경보가 있다.
- 서비스 테스트는 과거 조합 미반환, 전략별 적용, 순서 독립 마스크, 이벤트 갱신, 빈 DB·중간 누락 fail-closed, 충돌이 많은 입력과 속성 기반 불변식을 폭넓게 검증한다.

따라서 이 개선안은 기존 기능을 새로 만드는 작업이 아니라 **현재 애플리케이션 메모리 수준의 보장을 DB·다중 인스턴스·readiness·UI 계약까지 확장**하는 작업이다.

### 4.3 발견 당시 위험(해소됨)

#### A. 새 회차 커밋과 비동기 갱신 사이의 경쟁 구간

당첨 번호 트랜잭션이 커밋된 뒤 이벤트 리스너가 비동기로 스냅샷을 갱신한다. 그 짧은 구간에는 기존 스냅샷이 여전히 `ready=true`이며, 방금 DB에 들어온 조합을 과거 조합으로 인식하지 못할 수 있다.

#### B. 다중 인스턴스 캐시 불일치

Spring 애플리케이션 이벤트는 프로세스 로컬이다. 한 인스턴스가 새 당첨 번호를 저장해도 다른 인스턴스의 스냅샷은 자동으로 갱신되지 않는다. 현재 Compose는 백엔드 단일 컨테이너지만, 무중단 배포·수평 확장·향후 오케스트레이션에서는 장기적인 stale 상태가 될 수 있다.

#### C. DB 독립 방어선 부재

`winning_numbers`는 번호 자체의 정합성은 강하게 보장하지만 조합 마스크 열은 없다. `recommendation_items`는 번호를 문자열로 저장하며, 해당 조합이 부모 세트의 `history_through_round`까지 당첨 이력에 없는지 DB가 독립적으로 검증하지 않는다. 애플리케이션 결함이나 별도 데이터 입력 경로가 생기면 DB가 잘못된 저장을 막지 못한다.

#### D. readiness와 추천 이력 readiness의 분리

Docker healthcheck는 `/actuator/health/readiness`를 사용하지만, 현재 추천 이력 준비 여부는 Micrometer gauge와 경보일 뿐 Spring readiness 그룹의 필수 `HealthIndicator`가 아니다. 애플리케이션은 일반적으로 준비되었지만 추천 정책은 보장하지 못하는 인스턴스가 트래픽을 받을 수 있다.

#### E. API와 UI의 정책 표현 부족

응답에 `historyThroughRound`는 있지만 “역대 당첨 조합 제외가 실제 적용되었다”는 명시 필드와 정책 버전은 없다. 실제 추천 폼 가까이에도 상시 적용 정책이 뚜렷하게 보이지 않고, 방법론 페이지에서만 설명한다.

### 4.4 목표 구조

```text
winning_numbers 커밋
        │
        ├─ DB history_version 증가 / 최신 회차 확정
        ├─ 모든 인스턴스의 준비 상태 즉시 무효화
        └─ 조합 마스크 스냅샷 재구축
                     │
추천 요청 ── DB 버전 == 로컬 스냅샷 버전 확인
                     │
          불일치·결손이면 503 fail-closed
                     │
          모든 전략에서 역사 마스크 제외
                     │
          저장 시 DB 트리거/제약으로 재검증
                     │
응답: exclusionApplied=true + historyThroughRound + policyVersion
```

### 4.5 서버·백엔드 개선안

1. **단조 증가 이력 버전 도입**
   - DB에 단일 행 메타 테이블 또는 동등한 버전 소스를 둔다.
   - 당첨 번호 삽입·수정·삭제 트랜잭션과 같은 커밋 경계에서 `history_version`을 증가시킨다.
   - 스냅샷은 `version`, `historyThroughRound`, `roundCount`, `firstMissingRound`, `masks`를 함께 보유한다.

2. **요청 전 신선도 확인**
   - 추천 요청마다 가벼운 DB 버전 조회를 수행하거나 짧은 TTL의 신뢰 가능한 버전 캐시를 사용한다.
   - 로컬 스냅샷 버전과 DB 버전이 다르면 추천하지 않고 동기 재구축 또는 503을 선택한다.
   - 성능상 비동기 재구축을 유지하더라도, 당첨 번호 커밋 시 현재 인스턴스의 `ready`를 먼저 false로 바꾼 뒤 재구축해야 한다.

3. **다중 인스턴스 무효화**
   - 최소 보장은 요청 시 DB 버전 비교다. 메시지 브로커, DB 알림 또는 Redis pub/sub는 지연을 줄이는 최적화로 사용하되 유일한 정확성 근거로 삼지 않는다.
   - 이벤트 유실이 있어도 다음 요청의 DB 버전 비교로 stale 스냅샷 사용을 막아야 한다.

4. **추천 경로 단일화**
   - 저장형·비저장형, 공개 API·내부 호출, 모든 전략이 하나의 정책 검사와 생성 함수를 통과하도록 한다.
   - 새로운 전략을 추가할 때 역사 조합 제외 검사를 우회할 수 없는 타입·템플릿 메서드 구조를 사용한다.

5. **오류 계약 고정**
   - 데이터 없음, 회차 누락, 버전 불일치, 재구축 중을 모두 fail-closed로 유지한다.
   - 외부에는 안정적인 오류 코드와 재시도 가능 여부를 주고, 내부 지표에는 원인을 구분한다.

### 4.6 DB 개선안

1. **정규 조합 표현**
   - `winning_numbers`와 `recommendation_items`에 `combination_mask BIGINT`를 추가한다.
   - 1~45 번호를 각각 비트 0~44로 변환한 동일한 알고리즘을 애플리케이션과 마이그레이션에서 사용한다.
   - 기존 데이터를 백필한 뒤 `NOT NULL`로 전환하고 인덱스를 생성한다.

2. **인덱스**
   - `winning_numbers(combination_mask, round_no)` 인덱스를 둔다.
   - 필요하면 `recommendation_items(combination_mask)`도 감사·조사 용도로 인덱싱한다.

3. **저장 시 독립 검증**
   - `recommendation_items`의 `INSERT/UPDATE` 전에 부모 `recommendation_sets.history_through_round`를 조회한다.
   - 동일 마스크가 `winning_numbers`에 존재하고 `round_no <= history_through_round`이면 DB에서 저장을 거부한다.
   - 이 규칙은 “생성 시점에 이미 당첨된 조합”을 막는다. 추천 이후 미래 회차에서 우연히 같은 조합이 당첨되는 정상 상황은 과거 추천 데이터를 훼손하지 않아야 한다.

4. **마이그레이션 안전성**
   - 운영 데이터에서 번호 문자열 파싱 실패, 중복·범위 오류, 과거 조합 충돌을 사전 점검하는 dry-run SQL을 준비한다.
   - 백필 → 검증 쿼리 → 인덱스 → `NOT NULL`/트리거 순으로 잠금과 롤백 전략을 명시한다.
   - 애플리케이션 구버전과 신버전이 동시에 동작하는 배포 구간을 고려해 expand/migrate/contract 순서를 사용한다.

DB 트리거만으로는 저장하지 않는 즉시 추천 응답을 보호할 수 없다. 따라서 **요청 전 서버 검증이 1차 정확성 보장**, **DB 검증이 저장 경로의 2차 방어선**이어야 한다.

### 4.7 API·프론트엔드 개선안

권장 응답 메타데이터:

```json
{
  "recommendations": [[1, 7, 13, 22, 34, 41]],
  "strategy": "random",
  "algorithmVersion": "…",
  "historicalExclusionApplied": true,
  "historyThroughRound": 1200,
  "exclusionPolicyVersion": "historical-first-prize-v1"
}
```

- `historicalExclusionApplied`는 성공 응답에서 항상 `true`여야 한다. `false`인 성공 응답은 허용하지 않는다.
- 추천 폼의 전략 선택과 생성 버튼 가까이에 “역대 1등 당첨 조합은 항상 제외됩니다”를 표시한다.
- 체크박스나 토글로 표현하지 않는다. 필요하면 체크 아이콘과 “항상 적용” 배지를 사용한다.
- 결과 카드에는 “제1200회까지 확인”처럼 `historyThroughRound`를 사람이 이해할 수 있게 표시한다.
- 이력 미준비 503은 일반 서버 오류와 구분해 “당첨 이력을 완전히 확인하는 중이므로 추천을 잠시 중단했습니다”와 재시도를 제공한다.
- 공유된 추천 첨부와 저장 이력에도 생성 당시의 회차·정책 버전을 보여 감사 가능성을 유지한다.

### 4.8 readiness·관측 개선안

- 추천 이력 전용 `HealthIndicator`를 만들고 `ready`, DB 버전, 스냅샷 버전, 첫 누락 회차를 상세 정보로 제공한다.
- 이를 Spring readiness 그룹에 포함해 불완전하거나 stale한 인스턴스는 트래픽을 받지 않게 한다.
- liveness에는 포함하지 않는다. 데이터 결손 때문에 프로세스를 계속 재시작하는 루프가 생겨서는 안 된다.
- 지표를 다음처럼 확장한다.
  - `kraft_lotto_history_db_version`
  - `kraft_lotto_history_snapshot_version`
  - `kraft_lotto_history_snapshot_age_seconds`
  - `kraft_lotto_history_refresh_duration_seconds`
  - `kraft_recommendation_rejected_total{reason=...}`
- `db_version != snapshot_version`이 짧은 허용 시간을 넘거나 스냅샷 나이가 수집 주기를 초과하면 경보한다.
- 운영 runbook에 누락 회차 확인, 재백필, 스냅샷 재구축, readiness 복구 확인 순서를 적는다.

### 4.9 필수 테스트

| 계층 | 테스트 |
|---|---|
| 단위 | 세 전략 모두 과거 마스크를 반환하지 않음, 순서와 무관한 동일 마스크, 후보 충돌 한계 |
| 서비스 | 빈 DB·중간 누락·버전 불일치·재구축 중 503, 정상 복구 후 성공 |
| 경쟁 조건 | 새 당첨 번호 커밋 직후 갱신 완료 전 요청이 기존 스냅샷으로 성공하지 않음 |
| 다중 인스턴스 | A 인스턴스가 회차를 반영한 뒤 B 인스턴스가 stale 스냅샷으로 추천하지 않음 |
| DB | 마스크 백필 정확성, 과거 조합 추천 저장 거부, 미래 당첨과 기존 추천 공존 |
| API 계약 | 성공 시 exclusion 필드 true, 확인 회차·정책 버전 존재, 오류 코드 안정성 |
| UI | 상시 적용 문구, 결과 확인 회차, 503 전용 안내, 키보드·스크린리더 접근 |
| 운영 | 이력 미준비 인스턴스 readiness DOWN, 복구 후 UP, 경보와 runbook 연결 |

### 4.10 완료 조건

- 과거 당첨 조합을 반환할 수 있는 공개·내부 코드 경로가 없다.
- DB가 비었거나 1회부터 최신까지 한 회차라도 누락되면 추천 성공 응답이 없다.
- 신규 회차 커밋 직후와 다중 인스턴스에서도 stale 성공 응답이 없다.
- 저장형 추천은 애플리케이션을 우회해도 DB가 과거 조합을 거부한다.
- 성공 응답과 UI가 적용 정책과 확인 기준 회차를 명시한다.
- 이력 정책을 보장하지 못하는 인스턴스는 readiness에서 제외된다.

## 5. P0 — 개인정보·서비스 설명 정합성

### 5.1 개인정보처리방침이 실제 데이터 모델보다 좁다

`web/src/app/info/[slug]/page.tsx`의 개인정보처리방침은 회원가입 없이 이용하며 익명 기기 토큰과 저장 번호만 서버에 보관하고 이름·이메일·연락처 같은 직접 식별 정보를 기본적으로 수집하지 않는다고 설명한다.

하지만 백엔드에는 다음 데이터 처리 경로가 존재한다.

- Google·Naver OAuth 제공자와 제공자별 사용자 ID
- 닉네임과 프로필 이미지 URL
- 로그인 세션과 탈퇴 상태
- 게시글·댓글 작성자 스냅샷
- 좋아요 등 반응, 신고, 차단, 운영 조치
- 익명 기기 토큰과 저장 번호·추천 이력의 계정 귀속/이관
- 광고 네트워크와 서비스 로그

이메일을 저장하지 않는 설계 주석이 있더라도 “직접 식별 정보는 수집하지 않는다”와 “저장 번호만 보관한다”는 현재 서비스 전체를 설명하지 못한다.

개선 내용:

- 처리 항목, 목적, 법적 근거, 보유 기간, 파기 절차를 기능별로 명시한다.
- OAuth 제공자, 제공자 식별자, 닉네임, 프로필 이미지, 커뮤니티 활동, 신고·차단·세션, 기기 토큰, 운영 로그를 포함한다.
- 탈퇴 시 즉시 삭제·익명화·법적 보관 대상과 게시글 처리 방식을 실제 서비스 로직과 맞춘다.
- Kakao AdFit과 선택 가능한 AdSense 구성 중 실제 활성 공급자, 쿠키·광고 식별자, 국외 이전 가능성, 거부 방법을 배포 설정과 동기화한다.
- 문의·열람·정정·삭제·처리 정지 요청 절차와 책임자 정보를 명확히 한다.
- 법률 검토를 거친 문구를 사용하고 시행일·개정 이력을 관리한다.

완료 조건:

- 데이터 엔티티와 로그 화이트리스트를 기준으로 만든 처리 항목 목록과 정책 문구가 일치한다.
- OAuth 로그인·커뮤니티·탈퇴·기기 이관·광고 시나리오별 검토표가 있다.
- 정책 변경 시 테스트 또는 콘텐츠 스냅샷이 주요 필수 문구의 누락을 감지한다.

### 5.2 방법론·FAQ·약관 문구가 실제 전략과 다르다

- 방법론 페이지는 합계 구간을 `~100`, `101~150` 같은 50 단위로 설명하지만 실제 구간은 `21~65`, `66~110`, `111~155`, `156~200`, `201~255`다.
- 방법론은 모든 추천을 단순 무작위로 설명하는 문장과 별도의 분산 전략 설명이 섞여 있다.
- FAQ 구조화 데이터는 추천이 “완전 무작위”이며 특정 조합을 유리하게 만들지 않는다고 설명하지만, 실제로는 `balanced`와 `reduce_shared_winner_risk` 전략이 후보를 필터링·평가한다.
- 이용약관도 서비스를 무작위 추천 중심으로만 설명한다.
- “공동 당첨 분산형”, “공동 당첨 위험 완화” 등 동일 전략의 사용자 노출 이름이 다르다.

모든 조합의 1등 확률이 동일하다는 설명은 유지하되 다음을 구분해야 한다.

- 무작위 전략: 허용 후보에서 균등 추출
- 균형 전략: 정의된 통계 조건을 만족하도록 후보 선택
- 공동 당첨 위험 완화 전략: 당첨 확률을 높이지 않고 선택 편향이 덜한 조합을 우선
- 모든 전략 공통: 역대 1등 당첨 조합 상시 제외

합계 구간과 전략명은 가능하면 코드 상수 또는 공유 콘텐츠 모델에서 파생해 드리프트를 줄인다.

## 6. P1 — 프론트엔드 UX와 반응형 개선

### 6.1 모바일 당첨금 표의 핵심 금액 잘림

대표 모바일 기준 이미지에서 당첨금 영역의 “세후 예상 금액” 열과 실제 금액이 오른쪽에서 잘린다. 페이지 전체 가로 스크롤이 없다는 테스트는 통과하지만, 내부 컨테이너의 `overflow: hidden` 또는 허용된 오버플로 때문에 사용자가 핵심 정보를 읽지 못한다.

권장안:

- 639px 이하에서는 표를 순위별 세로 카드로 바꾼다.
- 한 카드 안에 `등수`, `당첨자 수`, `1인당 세전`, `세후 예상`을 2열 정의 목록으로 표시한다.
- 표를 유지한다면 의미 있는 가로 스크롤 영역, 스크롤 가능성 안내, 고정 첫 열, 양끝 그림자, 키보드 접근을 제공한다.
- 금액을 임의로 숨기거나 생략하지 않는다.

완료 조건:

- 320px 폭과 200% 확대에서 모든 열 제목과 금액을 읽을 수 있다.
- 페이지와 표 어디에도 의도하지 않은 클리핑이 없다.
- Playwright가 단순 `scrollWidth`뿐 아니라 마지막 금액 셀의 가시성 또는 스크롤 접근 가능성을 확인한다.

### 6.2 커뮤니티 목록의 한 행 압축

모바일 목록은 카테고리, 제목, 작성자, 조회·댓글·좋아요 정보를 한 줄 flex 행에 배치해 제목과 메타데이터가 지나치게 압축된다.

권장 모바일 레이아웃:

- 1행: 카테고리 배지 + 제목
- 2행: 작성자·작성 시각
- 3행 또는 오른쪽 그룹: 조회·댓글·좋아요
- 제목은 2줄까지 허용하고 긴 단어·URL도 안전하게 줄바꿈한다.
- 행 전체를 클릭 가능하게 만들더라도 내부 링크의 포커스 순서와 접근 가능한 이름을 명확히 한다.
- 44×44px 터치 목표와 충분한 행 간격을 보장한다.

### 6.3 데스크톱 추천 스튜디오의 불균형

현재 홈과 추천 화면의 데스크톱 추천 폼은 다열 그리드와 큰 번호판 사이에 빈 공간이 생기고, 우측 생성 버튼이 과도하게 큰 세로 막대처럼 보인다. 핵심 순서인 “전략 → 개수 → 번호 조건 → 생성”도 시선 흐름과 맞지 않는다.

권장안:

- 데스크톱: 좌측에 전략·개수·고정/제외 조건·일반 크기 CTA, 우측에 번호판과 결과를 두는 2열 구조
- 태블릿: 컨테이너 폭에 따라 1열 또는 2열로 전환
- 모바일: 자연스러운 1열 순서와 하단 고정 내비게이션을 고려한 충분한 마지막 여백
- 페이지 전체 브레이크포인트보다 추천 컴포넌트 컨테이너 쿼리를 우선 검토
- 홈에서는 전체 스튜디오를 그대로 노출할지, 빠른 추천과 상세 화면 링크로 줄일지 사용자 행동 지표로 판단

### 6.4 실패와 빈 상태를 분리

#### 홈 커뮤니티 요약

`getHomeSummary` 실패를 `null`로 바꾼 뒤 최신 글과 주간 인기 글 모두 “아직 글이 없습니다”로 표시한다. 이는 실제 데이터 없음과 서버 장애를 구분하지 못한다.

#### 계정 보관함

계정의 저장 번호와 추천 이력 요청 실패를 빈 배열로 바꾸고, 둘 다 비어 있으면 섹션 자체를 렌더링하지 않는다. 사용자는 데이터가 없는지 불러오지 못했는지 알 수 없다.

#### 삭제 작업

추천 이력 삭제 실패는 오류를 삼키며, 저장 번호 지연 삭제도 실패 후 복구만 하고 명확한 상태를 제공하지 않는다.

모든 데이터 컴포넌트는 다음 상태를 명시적으로 가져야 한다.

```text
idle/loading → success(data | empty)
             → error(retryable | terminal)
```

- 빈 상태에는 기능 설명과 다음 행동을 제공한다.
- 오류 상태에는 원인에 맞는 문구, 다시 시도, 필요하면 상태 페이지 링크를 제공한다.
- 삭제·복구 결과는 `aria-live` 상태 또는 접근 가능한 토스트로 알린다.
- 낙관적 업데이트 실패 시 원래 항목, 포커스, 정렬 위치를 정확히 복원한다.

### 6.5 상시 제외 정책을 실제 추천 흐름에 표시

방법론 페이지에만 있는 역사 조합 제외 안내를 추천 입력과 결과로 가져온다.

- 전략 선택 아래: “모든 전략에서 역대 1등 당첨 조합은 항상 제외됩니다.”
- 생성 버튼 주변: 선택 가능한 옵션처럼 보이지 않는 “항상 적용” 상태
- 결과: “제N회까지의 당첨 이력과 비교 완료”
- 오류: 이력 확인 불가 시 왜 추천을 중단했는지 설명

이는 백엔드 정확성을 대체하는 UI 기능이 아니라 사용자가 서버 정책을 확인할 수 있게 하는 계약 표현이다.

### 6.6 접근성 프리미티브

#### `SegmentedControl`과 `Tabs`

화살표 키가 선택값은 바꾸지만 새 항목으로 실제 DOM 포커스를 이동하지 않는다. 기존 요소가 `tabIndex=-1`로 바뀌어도 포커스가 남아 로빙 포커스 패턴이 불완전하다.

- 방향키 선택 후 새 활성 요소에 `.focus()`를 적용한다.
- Home/End, 좌우 또는 상하 방향, 비활성 항목 건너뛰기를 명세한다.
- 테스트는 `aria-checked`/값뿐 아니라 `document.activeElement`를 검증한다.

#### Dialog·Drawer 포커스 트랩

포커스 가능한 자식이 없을 때 컨테이너에 초점을 주려 하지만 컨테이너 자체가 포커스 가능하지 않을 수 있다. 배경 `inert`와 body scroll lock도 명확하지 않다.

- 패널에 안전한 `tabIndex=-1`과 적절한 `role`, 레이블 연결을 보장한다.
- 열릴 때 첫 의미 요소 또는 패널, 닫힐 때 호출 요소로 포커스를 복귀한다.
- 배경을 `inert`/`aria-hidden` 정책에 맞게 비활성화하고 모바일 body scroll을 잠근다.
- 포커스 가능한 자식 없음, 중첩 스크롤, Escape, 바깥 클릭, 호출 요소 제거 시나리오를 테스트한다.

### 6.7 고정 모바일 내비게이션

하단 내비게이션은 safe area 하단 여백을 사용하지만 스크롤 중 현재 콘텐츠 위를 덮고, 낮은 화면·가상 키보드에서는 폼 조작을 방해할 수 있다.

- `env(safe-area-inset-bottom)`과 실제 바 높이를 하나의 토큰으로 사용한다.
- 모든 페이지의 마지막 포커스 가능 요소가 바 위로 스크롤될 수 있게 `scroll-padding-bottom`을 적용한다.
- 가상 키보드 표시 중 동작과 Android/iOS의 visual viewport 차이를 확인한다.
- 844×390 가로 화면뿐 아니라 320×568, 375×667 같은 낮은 세로 화면을 추가한다.

## 7. P1 — 프론트엔드 구조와 테스트

### 7.1 전역 CSS와 브레이크포인트

`web/src/app/styles/layout.css`는 약 706줄이며 모바일 기본, 모바일 전용, 태블릿, 데스크톱 규칙과 이전 선언을 다시 덮는 예외가 한 파일에 공존한다. CSS와 TypeScript에 브레이크포인트 지식이 중복되고 문자열 동기화 테스트에 의존한다.

권장 단계:

1. `@layer reset, tokens, primitives, components, utilities, overrides`로 우선순위를 선언한다.
2. 페이지·도메인별 규칙을 컴포넌트 인접 CSS Module 또는 명시적 레이어 파일로 이동한다.
3. 모바일 기본 스타일에서 출발하고 상위 폭에서 필요한 차이만 추가한다.
4. 페이지 폭이 아니라 실제 컴포넌트 가용 폭이 중요한 추천 폼·카드 묶음에는 컨테이너 쿼리를 적용한다.
5. 브레이크포인트는 문서, CSS custom media 생성 또는 빌드 산출 경로 중 하나를 단일 진실 공급원으로 정한다.
6. 의도적 오버플로는 전용 유틸리티와 접근성 요구를 함께 정의하고 임의의 `overflow:hidden`을 줄인다.

정적 클래스 대조에서는 리터럴 클래스 144개 중 미정의로 보인 항목은 광고 공급자용 `adsbygoogle`, `kakao_ad_area`뿐이었다. 따라서 현재 문제는 “대량의 없는 클래스”가 아니라 **정의가 한 전역 파일에 집중되고 예외 관계가 복잡한 것**이다.

### 7.2 UI 프리미티브의 실제 사용률

TSX 프리미티브 21개 중 프로덕션에서 확인된 사용은 Badge, Dialog, Divider, Drawer, IconButton, SegmentedControl, Surface 등 7개 정도다. Button, Chip, EmptyState, ErrorState, InlineAlert, NumberField, SearchField, Section, Skeleton, StatusBadge, Tabs, TextArea, TextField, Toast 등은 테스트만 있거나 실제 화면에서 사용되지 않는다.

둘 중 하나를 선택해야 한다.

- 공용 디자인 시스템으로 유지: 주요 화면의 원시 입력·버튼·상태 UI를 단계적으로 이전하고 사용률·접근성 계약을 관리
- 제품에 필요하지 않음: 추측성 프리미티브와 관련 CSS·테스트 제거

프리미티브 수 자체를 늘리는 것을 목표로 하지 말고, 실제 반복 문제와 접근성 계약을 줄이는 것을 목표로 한다.

### 7.3 API 타입의 이중 관리

공개 일부 스키마는 생성된 `api-types.ts`를 사용하지만 홈 요약·분석 타입과 커뮤니티 계약 다수는 수동 타입으로 중복 정의된다. 현재 API 드리프트 검사는 생성 파일이 실행 중인 백엔드 명세와 맞는지는 확인하지만, 수동 타입이 생성 계약과 맞는지는 보장하지 않는다.

- OpenAPI 생성 타입을 원시 계약으로 사용한다.
- UI가 원하는 non-null·날짜·열거형 형태는 얇은 정규화 함수에서 변환한다.
- 수동 응답 인터페이스 복제를 제거한다.
- 정규화 함수는 누락 필드, 알 수 없는 enum, 잘못된 날짜를 명시적으로 처리하고 테스트한다.

### 7.4 Next.js API 프록시 중복

약 20개의 route handler가 백엔드 경로, 쿼리, 본문, 헤더와 쿠키 전달을 수동으로 반복한다. 운영 Caddy 경로에서는 우회되며 주로 로컬 개발을 위해 존재해, 개발과 운영 동작이 달라질 수 있다.

대안:

- 보안상 허용된 경로·메서드·헤더만 처리하는 중앙 catch-all 프록시
- 또는 로컬에서도 Caddy 동일 출처 구성을 표준 개발 경로로 사용

유지한다면 모든 라우트에 대해 메서드, 검색 파라미터, 콘텐츠 타입, 캐시·ETag, `Set-Cookie`, 오류 본문 전달의 계약 테스트가 필요하다.

### 7.5 CSP nonce로 인한 전 경로 동적 렌더링

현재 proxy에서 모든 요청에 nonce를 만들기 때문에 빌드 결과의 페이지가 동적 경로로 분류된다. CSP 강도를 낮추기 전에 실제 TTFB, CDN 캐시 적중률, 정적 정보 페이지 트래픽을 측정해야 한다.

- 정보·정책 페이지를 nonce 요구 없이 안전하게 정적화할 수 있는지 Next.js 현재 권장 패턴을 검토한다.
- Caddy에서 생성하는 CSP와 애플리케이션 nonce의 책임을 비교한다.
- 보안 회귀 없이 의미 있는 TTFB·캐시 개선이 증명될 때만 구조를 바꾼다.

현재 번들 크기는 예산 이내이므로 무분별한 lazy loading이나 청크 분할보다 렌더링·캐시 구조 측정이 우선이다.

### 7.6 크로스 브라우저와 의미 기반 시각 검증

감사 시작 시 Firefox·WebKit용 Playwright 설정은 있었으나 CI 핵심 흐름은 모두 Chromium 엔진이었다. 또한 120개 시각 기준 이미지는 변경 검출에는 유용하지만 모바일 당첨금 잘림처럼 승인 당시 이미 존재한 품질 문제를 실패로 만들지 못했다.

- PR smoke: Chromium + WebKit의 홈, 추천, 저장, 커뮤니티 핵심 흐름
- 정기 실행: Chromium, Firefox, WebKit 전체 반응형·접근성
- 의미 검증: 핵심 금액·버튼·오류 문구가 viewport 또는 접근 가능한 스크롤 영역에 존재하는지 검사
- 경계 폭: 기존 320, 639, 768, 1023, 1024, 1280에 정확한 640과 1440·1920 추가
- 낮은 높이·확대: 320×568, 375×667, 가로 화면, 폼 페이지 200% 확대
- 모바일 실제 차이: iOS WebKit safe area, Android 글자 크기 확대, 가상 키보드

조건부로 건너뛰는 coarse pointer 터치 목표 검사도 CI 프로젝트 특성에 맞게 실제로 실행되도록 분리한다.

## 9. P1/P2 — 백엔드·DB·운영 개선

### 9.1 API 드리프트 검증의 로컬 재현성

`verify:api-types`는 실행 중인 `localhost:8080` 명세가 필요하다. CI에서는 유효하지만 로컬에서 백엔드 미기동이면 타입 불일치와 환경 실패를 구분하기 어렵다.

- 검증 스크립트가 “백엔드 연결 실패”와 “생성 파일 차이”를 다른 코드·메시지로 반환한다.
- 한 명령으로 임시 백엔드를 띄우거나 저장된 OpenAPI 산출물을 생성할 수 있는 표준 경로를 제공한다.
- CI 산출물로 명세와 생성 타입 diff를 보관한다.

### 9.2 데이터베이스 문자열 번호 표현

`saved_numbers`와 `recommendation_items`의 번호 조합이 `VARCHAR` 중심이라 정렬·중복·범위 정합성이 애플리케이션 정규화에 의존한다.

- 추천의 역사 마스크 개선과 함께 정규 조합 마스크를 도입한다.
- 문자열은 표시·호환용으로 유지하더라도 DB 비교·유니크·감사 기준은 정규 마스크를 사용한다.
- 저장 번호에도 동일 조합의 다른 문자열 표현이 중복되지 않도록 마스크 유니크 키를 검토한다.

최종 결정: 추천·당첨 조합에는 V29의 `combination_mask`를 적용했다. 저장 번호는 입력 즉시
`LottoNumberCodec`의 오름차순 단일 문자열로 정규화되고 기기·계정 소유자별 유니크 키가
동일 조합을 차단하므로 별도 마스크가 데이터 무결성을 추가로 높이지 않는다. 따라서 저장
번호 마스크 도입은 중복 인덱스와 마이그레이션 위험만 늘리는 것으로 판단해 적용하지 않는다.

### 9.3 부하·동시성 검증을 릴리스 근거로 연결

`scripts/load-test/recommend-and-community.js`가 있지만 일반 CI는 API·DB 동시성 성능을 정기적으로 평가하지 않는다. Lighthouse와 번들 예산은 서버 추천, 커뮤니티 인기 정렬, DB 잠금 경합을 측정하지 못한다.

- 배포 전 또는 정기 환경에서 추천 생성, 저장·삭제, 커뮤니티 목록·상세를 혼합한 k6 시나리오를 실행한다.
- p50/p95/p99, 오류율, DB 풀 대기, 추천 충돌 재시도, GC, 쿼리 시간을 함께 수집한다.
- 역사 버전 요청당 조회를 도입할 때 성능 기준을 먼저 정하고 인덱스·TTL을 조정한다.
- 정확성 테스트와 성능 테스트를 분리하지 말고, 부하 중에도 역사 조합 불변식을 표본 검증한다.

저장소에서 가능한 준비는 임계값과 역사 조합 표본 검사를 포함한 k6 시나리오까지 완료했다.
다만 운영과 격리된 성능 환경, 대표 데이터, 실행 용량은 저장소 밖 의존성이므로 릴리스 게이트
실행은 차단 상태다. 운영 서버에 직접 부하를 가하지 않는다는 안전 원칙을 우선한다.

### 9.4 코드 주석과 삭제된 문서 참조

여러 소스와 CI 주석이 `docs/improvement_gpt.md`, `docs/phase0-design-tokens-mapping.md`, `docs/phase0-photo-asset-policy.md` 같은 현재 존재하지 않는 문서를 가리킨다. `docs/*.md`는 `.gitignore`에서 기본적으로 로컬 전용이므로 장기 계약의 근거로도 부적합하다.

## 10. P2/P3 — 정보 구조와 제품 경험

### 10.1 홈의 전체 추천 스튜디오 노출

모바일 홈에서 전체 추천 폼과 번호판이 긴 영역을 차지해 커뮤니티와 다른 탐색 진입점이 아래로 밀린다. 다음 두 안을 실험한다.

- 빠른 추천: 전략 기본값, 개수, 생성만 제공하고 상세 조건은 `/recommend`로 연결
- 접이식 상세: 첫 생성에 필요한 최소 컨트롤만 보이고 고정·제외 번호는 확장

클릭률, 추천 완료율, 상세 추천 진입률, 홈 이탈률을 기준으로 결정한다. 기능을 임의로 축소하지 않는다.

이 항목은 실제 사용자 행동 표본과 제품 지표 결정이 필요한 A/B 실험이다. 저장소만으로 어느
안을 채택해야 하는지 검증할 수 없어 외부 의존성으로 분류하며, 근거 없이 기능을 축소하지 않는다.

### 10.2 콘텐츠 메타데이터 관리

정책 시행일, sitemap의 `lastModified`, 전략 설명과 FAQ 구조화 데이터가 서로 독립적으로 하드코딩되어 쉽게 오래된다.

- 정보 페이지별 콘텐츠 메타 모델에 제목, 설명, 시행일·개정일, 검색 노출 여부를 함께 둔다.
- 화면, sitemap, JSON-LD가 같은 데이터를 소비하게 한다.
- 정책 변경 PR에서 시행일과 sitemap 갱신 여부를 자동 검사한다.
