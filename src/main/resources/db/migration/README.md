# 마이그레이션 규칙 (A-OPS-03)

배포는 단일 인스턴스를 재시작하는 방식이다(`deploy/deploy-apply.sh`) — 새 jar가 기동해
`ddl-auto: validate`를 통과해야 서비스가 다시 올라온다. 롤백은 jar만 되돌리고 **DB는
되돌리지 않는다**. 새 jar가 적용한 마이그레이션이 옛 jar와 호환되지 않으면(컬럼 삭제·이름
변경), 롤백한 옛 jar가 스키마 검증에서 기동 실패한다 — 롤백이 가장 필요한 순간에 실패하는
구조다.

## 확장 → 배포 → 수축

컬럼·테이블을 **삭제하거나 이름을 바꾸는** 마이그레이션은 절대 한 번에 배포하지 않는다.
대신 세 단계로 나눈다.

1. **확장(expand)**: 새 컬럼/테이블을 추가만 한다. 기존 컬럼은 그대로 둔다. 애플리케이션은
   아직 옛 컬럼을 쓴다.
2. **배포(migrate)**: 애플리케이션이 새 컬럼을 쓰도록 바꿔 배포한다. 옛 컬럼은 코드에서
   더 이상 읽거나 쓰지 않지만 스키마에는 남아 있다 — 이 상태에서 **옛 jar로 롤백해도
   여전히 기동한다**(옛 컬럼이 그대로 있으므로).
3. **수축(contract)**: 1·2가 문제없이 운영에서 돌아간 뒤, **별도 커밋·별도 배포**로 옛
   컬럼/테이블을 삭제하는 마이그레이션을 추가한다. 이 시점부터는 그 배포 이전으로 롤백할
   수 없다는 것을 받아들인 것이다.

`V24__hash_one_time_tokens.sql`이 정확히 이 패턴을 따른다: `token_hash` 컬럼을 먼저
추가하고(확장) 채운 뒤, 같은 파일 안에서 옛 `token` 컬럼을 지웠다(수축) — 토큰 해시화처럼
"되돌릴 이유가 없는" 보안 수정은 1·2·3을 한 파일로 압축해도 되지만, **일반적인 스키마
변경은 이렇게 하지 않는다**. 애매하면 세 단계로 나눈다.

## CI 경고

`.github/workflows/build.yml`의 "Warn on destructive DDL in new migration files" 스텝이
이번 푸시에서 **새로 추가된** `V*.sql` 파일에 `DROP COLUMN`·`DROP TABLE`·`RENAME COLUMN`·
`RENAME TABLE`·`CHANGE COLUMN`이 있으면 경고를 남긴다(빌드를 막지는 않는다 — 위
`V24`처럼 의도된 경우가 있어서다). 경고가 뜨면 위 3단계 중 어느 단계인지, "수축" 단계라면
그 전 "확장·배포" 단계가 이미 운영에 배포되어 있는지 스스로 확인한다.
